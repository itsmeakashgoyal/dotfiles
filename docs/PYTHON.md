# Python: mise + uv

Two tools, two jobs, no overlap:

- **[mise](https://mise.jdx.dev/)** decides *which Python (and Node, and any other
  runtime) interpreter version* is on your `PATH`. Cross-platform (macOS/Linux/Windows),
  one tool for every language you pin.
- **[uv](https://docs.astral.sh/uv/)** does *everything about the actual Python
  environment* — creating venvs, installing packages, lockfiles — using whichever
  interpreter mise put on `PATH` (or a specific one you tell it to fetch itself).

Neither tool knows about the other; they just compose because uv defaults to
"whatever `python` resolves to right now," and mise's job is making that resolve
to the right thing.

```text
mise  → picks the interpreter version (python 3.12, node 20, ...)
 uv   → creates the venv + installs/locks packages, using that interpreter
```

This split matters most once you have several unrelated projects going at once —
AI/ML experiments needing different (and often conflicting) heavy dependencies,
plus internal projects that need Node — which is exactly the case this is set up for.

## mise: picking interpreter versions

### Install a Python version

```bash
mise install python@3.12        # download + install a specific version
mise install python@3.12.4      # exact patch version
mise ls-remote python          # see everything available
```

### Set which version is active

```bash
# Globally (all shells, unless overridden per-project)
mise use --global python@3.12

# Per-project (writes mise.toml in the current directory)
cd ~/projects/my-ml-project
mise use python@3.12
```

`mise use` (no `--global`) creates/updates a `mise.toml` file in the current
directory. `cd` into that directory in any shell and mise activates that version
automatically — no manual switching needed. This is the main reason to prefer it
over a global-only setup: each project directory can pin its own version.

```toml
# mise.toml (auto-generated by `mise use python@3.12`)
[tools]
python = "3.12"
```

Commit `mise.toml` to a project's repo so teammates (or CI) get the same
interpreter version automatically.

### See what's active / installed

```bash
mise current              # what's active in this directory right now
mise ls                   # all installed versions, across all tools
which python               # confirm it resolves to mise's shim
```

### Node and other runtimes

Same commands, different tool name — this is the entire point of using mise
instead of a Python-only version manager:

```bash
mise install node@20
mise use node@20           # global
cd ~/projects/internal-app && mise use node@20   # per-project
```

## uv: venvs and packages

### Quick workflow (dotfiles helper functions)

`mkvenv`/`venv`/`rmvenv` work identically on macOS, Linux, and native Windows —
same names, same arguments, same behavior. `zsh/.config/zsh/conf.d/08-python.zsh`
defines them for zsh (macOS/Linux/WSL2); `powershell/.../Microsoft.PowerShell_profile.ps1`
defines the same three for native Windows PowerShell. The only thing that
differs under the hood is which activation script gets sourced (`bin/activate`
vs. `Scripts\Activate.ps1`) — uv creates the right one for the OS it's running
on, and both function sets look for it automatically.

| Command | What it does |
| --- | --- |
| `mkvenv` | Create **and activate** `.venv` in the current directory |
| `mkvenv myenv` | Create and activate a venv named `myenv` instead of `.venv` |
| `mkvenv .venv 3.11` | Create using a specific Python version (passed to `uv venv --python`) |
| `venv` | Activate an existing `.venv` (or `venv <name>`) without creating it |
| `rmvenv` | Deactivate (if active) and delete `.venv` (or `rmvenv <name>`) |

```bash
cd ~/projects/my-ml-project
mkvenv                              # creates + activates ./.venv using mise's active python
uv pip install torch numpy pandas   # install packages - see below
deactivate                          # standard venv deactivation, built into every venv
rmvenv                              # delete it when you're done with it
```

### Installing packages

uv's `pip` interface is a drop-in, much faster replacement — same commands you
already know, just prefixed with `uv`:

```bash
uv pip install requests                     # single package
uv pip install -r requirements.txt          # from a requirements file
uv pip install -e .                         # editable install of the current project
uv pip uninstall requests                   # remove a package
uv pip list                                 # what's installed
uv pip show requests                        # details on one package
uv pip freeze > requirements.txt            # snapshot current versions
```

None of these need pip itself installed in the venv — uv does the installing
directly. (`uv venv` deliberately does **not** seed pip/setuptools/wheel into new
venvs by default, since uv doesn't need them — pass `--seed` to `uv venv` if some
tool you use genuinely shells out to `pip` directly instead of using uv.)

### Reproducible installs (lockfiles)

For anything you'll come back to later or share (which — for AI/ML work — is most
things, given how easily a `pip install` today and one in three months can resolve
to different transitive versions):

```bash
uv pip compile requirements.in -o requirements.txt   # resolve + pin exact versions
uv pip sync requirements.txt                          # install exactly what's pinned
```

`compile` is the resolve step (like `pip-tools`, but far faster); `sync` makes the
venv match the lockfile exactly, installing missing packages *and* removing
anything not listed — useful when pulling someone else's project.

### Activating, deactivating, switching between environments

Nothing uv-specific here — `uv venv` creates a completely standard venv, so the
usual mechanics apply:

```bash
source .venv/bin/activate     # activate (or just: venv)
deactivate                     # leave it - built into every venv, no uv/mise involved
```

**Switching between multiple environments** is just deactivate-then-activate (or
`cd` + activate, since each project's venv lives in its own directory):

```bash
cd ~/projects/ml-experiment-a
source .venv/bin/activate       # or: venv
# ... work ...
deactivate
cd ~/projects/ml-experiment-b
source .venv/bin/activate       # or: venv
```

Your prompt shows `(venv-name)` while one is active, so it's always visible which
environment (if any) you're in.

### Multiple environments for AI/ML work

Give each project its own venv in its own directory — that's the natural way uv
already works, and it's what keeps conflicting dependencies (different
torch/CUDA/numpy pins across experiments) fully isolated:

```bash
cd ~/experiments/vision-model && mkvenv          # .venv here, isolated
cd ~/experiments/nlp-model && mkvenv .venv 3.12  # separate .venv, maybe a different Python version
```

If you'd rather name environments explicitly instead of one `.venv` per directory:

```bash
mkvenv envs/vision
mkvenv envs/nlp
venv envs/vision      # activate whichever one you need
```

### uv's project mode (alternative to the venv/pip workflow above)

Everything above mirrors the classic pip+venv workflow. uv also has a newer,
more structured **project mode** — worth knowing about for a real project you'll
keep working on, since it manages the venv *and* a lockfile for you automatically:

```bash
uv init my-project && cd my-project    # creates pyproject.toml + git repo
uv add torch numpy pandas               # adds to pyproject.toml, updates uv.lock, installs
uv add --dev pytest                      # dev-only dependency
uv run python train.py                   # runs inside the project's venv automatically
uv sync                                  # recreate the venv exactly from uv.lock (e.g. on a new machine)
```

In project mode you never manually activate anything — `uv run` finds
`pyproject.toml`, ensures `.venv` matches `uv.lock`, and runs your command inside
it. Use this for a project with real staying power; use `mkvenv`/`venv`/`rmvenv`
above for quick, throwaway, or exploratory environments.

## Quick reference

| Task | Command |
| --- | --- |
| Install a Python version | `mise install python@3.12` |
| Pin a project to a version | `mise use python@3.12` (run inside that project's directory) |
| See active version | `mise current` |
| Create + activate a venv | `mkvenv` (or `mkvenv <name>`, or `mkvenv <name> <py-version>`) |
| Activate an existing venv | `venv` (or `venv <name>`) |
| Deactivate | `deactivate` |
| Delete a venv | `rmvenv` (or `rmvenv <name>`) |
| Install packages | `uv pip install <pkg>` |
| Install from requirements.txt | `uv pip install -r requirements.txt` |
| Lock dependencies | `uv pip compile requirements.in -o requirements.txt` |
| Install from a lockfile exactly | `uv pip sync requirements.txt` |
| New structured project | `uv init <name>` |
| Add a dependency (project mode) | `uv add <pkg>` |
| Run inside a project's venv | `uv run <command>` |

## Troubleshooting

**`mkvenv`/`venv`/`rmvenv`: "uv is not installed"**
→ `brew install uv` (macOS) / already in `nix/home.nix` on Linux / already in
`scripts/setup/windows.ps1`'s Scoop package list on Windows. Re-run `make install`
or install it directly, then open a new shell.

**A freshly created venv's `python --version` isn't what you expected**
→ `uv venv` uses whatever `python` mise currently resolves to. Run `mise current`
first, or pass an explicit version: `mkvenv .venv 3.12`.

**`pip: command not found` inside an activated uv-created venv**
→ Expected — uv doesn't seed pip into new venvs by default. Use `uv pip install`
instead of `pip install`, or recreate with `uv venv --seed .venv` if you need a
real `pip` binary for something that shells out to it directly.

**Need mise to also manage Node/Ruby/Go/etc. for internal projects**
→ Same pattern as Python: `mise install node@20`, `mise use node@20` (global or
per-project `mise.toml`). uv only ever touches the Python side.
